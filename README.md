# Xclipse GPU Lab 0.15 alpha
Laboratório Android ARM64 de diagnóstico de GPU. Não contém llama.cpp, modelos de IA, internet, nem treinamento. Projetado para Xclipse 940 / Exynos 2400(e), mas as consultas públicas podem funcionar em outras GPUs.

## Funcionalidades implementadas no código
- Vulkan: versão, driver, IDs, extensões de instância/dispositivo, layers, filas, limites selecionados, features selecionadas, formatos core, memória e orçamento (quando anunciado), subgroup, FP16/INT8, dot product acelerado, mesh, ray tracing, cooperative matrix (formas/tipos), nomes e metadados de contadores de performance. As estruturas de extensão são consultadas apenas quando anunciadas ou promovidas ao core aplicável.
- EGL / GLES: contexto pbuffer próprio, renderer, versões, extensões e limites selecionados.
- OpenCL: tenta carregar a biblioteca pública libOpenCL.so, enumera plataformas e dispositivos, extensões e compute units. O Android pode bloquear a biblioteca por namespace. Ausência de acesso não prova ausência física.
- Kernel/SGPU: propriedades, nós devfreq, DRM, dumpsys gpu, arquivos de diagnóstico e térmicos GPU; root opcional, apenas se o dispositivo já o oferece. Sem exploit, sem mudança de permissões, sem escrita em sysfs/debugfs, sem desativar SELinux. Sensores e unidades são específicos da ROM; valores brutos são mostrados sem inventar porcentagens/Hz/temperaturas. O monitor reconsulta aproximadamente a cada 2 s após a leitura, apenas com a tela ativa.
- Bibliotecas ELF: lista arquivos acessíveis em diretórios gráficos, classe/arquitetura ELF, SHA-256, busca de strings VK/GL/EGL/CL, gfx11, WMMA e wave. Não descompila código, não lê áreas protegidas por root e não prova que as strings sejam símbolos exportados. Faça a consulta Vulkan antes da análise ELF para comparar strings VK_ não anunciadas; strings podem vir do loader, tabelas genéricas ou caminhos mortos. Limite 6000 pistas por arquivo.
- Investigação de extensão: processo de app separado (:probe), não isolado por UID. Teste de criação de dispositivo para quatro extensões selecionadas e anunciadas em Vulkan >=1.2; outras são apenas classificadas. Não habilita feature bits nem executa comandos específicos; dependências complexas ficam pendentes. Sem substituição de biblioteca ou configuração global. Uma falha de driver ainda pode afetar o sistema; não é uma sandbox do kernel.
- Exportação TXT via seletor Android e cópia do último relatório; compare manualmente relatórios de ROMs. Nenhum upload automático.

## Significado dos resultados
1. ANUNCIADA: o driver/loader declara a extensão.
2. ACEITA: vkCreateDevice aceitou a extensão na configuração testada; não comprova correção funcional.
3. INDÍCIO ELF: string presente, sem comprovação de código ou silício.
4. NÃO ANUNCIADA: não exposta pela API consultada. Não significa que seja possível ativá-la nem que esteja fisicamente ausente.
5. INDISPONÍVEL: consulta não acessível, não implementada, ou bloqueada pelo sistema.

A especificação exige que o driver rejeite extensões indisponíveis. Root não é uma chave universal de desbloqueio. A v0.1 não força extensões ocultas, não modifica o driver proprietário, não instala RADV, não captura registradores MMIO e não executa microbenchmarks de shaders/ISA. Contadores são enumerados, não amostrados via performance queries. A análise de driver alternativo e microtestes com resultados conhecidos são próximos passos.

- Android SDK 35, NDK 27.2.12479018, CMake 3.22.1, JDK 17, Gradle 8.9; headers Vulkan v1.4.321.

## Validação e limitações
O ambiente de criação não tem Android SDK/NDK, Gradle ou headers Vulkan. APK e código JNI não foram compilados/executados aqui. Os módulos Java independentes Kernel/Libraries foram compilados com javac; comparação sintética de strings e sintaxe do shell foram verificadas. O funcionamento no S24 FE, acesso ao root, estabilidade e disponibilidade de sensores dependem de testes reais. O APK deverá ser tratado como alpha.

## 0.6 — MGFX2 / cross-driver research
- ISA catalog: parse mnemonics, architecture and wave tags, and instruction words from driver-reported disassembly. Compare imported equivalent compute logs (Samsung vs RADV/ACO). Exact word mismatch is not proof of opcode incompatibility; operands and register allocation affect encoding.
- Vulkan functional tests: SPIR-V OpSDotKHR INT8/INT16, FP32 buffer atomic add when feature is advertised, 4x4 matrix multiplication via ALU/subgroup shuffle without cooperative matrix extension. Optional shaders that cannot be built are reported as SKIP. Tests need the required active-driver features, not raw opcode injection.
- OpenCL own kernels: UINT32, INT8 arithmetic, scalar INT16 dot expression, FP16 where advertised. Binary returned by compiler exported as hex (up to 256 KiB per kernel); AMD topology attributes queried if extension is advertised. Scalar dot is not native dot evidence.
- Cross-API topology and evidence report: driver-declared CU counts, private extension advertising and ELF hints, user-reported RADV Mesh Shader and ALU/subgroup cooperative matrix fallback. Not advertised does not imply absent hardware. Native WMMA remains undetermined. No private extension commands invoked; no driver modifications.
- Complete collection now includes 12 reports, including ISA catalog, OpenCL functional and topology evidence. Build/test via CI; device validation required.

## 0.9 — investigação FMA MGFX2 para RADV/ACO
- Arquitetura → **FMA MGFX2 / RADV** executa uma nova bateria em processo separado. **Evidências FMA / ACO** reúne resultados por shader e as palavras de instruções retornadas pelo driver. Coleta completa passa a 19 relatórios.
- Nove shaders SPIR-V: `fma` escalar por componente, `fma` de vetor FP16 de dois componentes e multiplicação/soma com `precise`/`NoContraction`; cada caminho com modo padrão, RTE16 e RTZ16. Cada shader é tentado em subgroup padrão, Wave32 e Wave64: até 27 configurações, somente com features/modos anunciados.
- Corpus determinístico de 128 triplas FP16, obtidas de buffers em tempo de execução, com operandos diferentes nas metades baixa/alta, sinais variados, empates de arredondamento e cancelamento que diferencia fusão. Oráculo inteiro exato em unidades de 2^-48; classifica correspondência com fused-RTE, fused-RTZ, split-RTE e split-RTZ. Corpus exclui subnormais/NaN/infinito, e o comparador ignora sinal de zero. Modos explicitamente solicitados são verificados apenas no controle split; `GLSL.std.450 Fma` é observacional porque Vulkan não garante fusão para essa instrução.
- Cada pipeline executa duas vezes. A segunda execução muda somente o primeiro componente de A na lane 0; registra se outros 127 componentes mudaram. Nenhum shuffle é usado nesse shader. O resultado caracteriza o shader completo: não isola uma única instrução, não demonstra um datapath coletivo e não prova ou refuta WMMA.
- Exporta operandos/resultados FP16 em hexadecimal, quatro referências por elemento e fase, tamanho de subgroup reportado pelo shader, versão do compilador SPIR-V e impressão FNV-1a de cada binário. A captura existente de ISA AMD/KHR e registradores permanece vinculada ao mesmo teste. Não é benchmark.
- Interpreta `OP[22:16]` para palavras que seguem o cabeçalho VOP3P e mostra referência RDNA3 para FMA/WMMA, sem equiparar semanticamente a variante Samsung `hp` em 0x1e a `mixlo` 0x21 ou WMMA 0x40. Nenhuma instrução bruta é injetada, nenhum recurso não anunciado é forçado e nenhum driver é modificado.
- Corrige o shader scalar/vector anterior para solicitar a extensão GLSL subgroup ballot necessária a `subgroupBroadcastFirst`, com verificação do bit Vulkan correspondente.
- Build exige glslc, spirv-dis, spirv-as e spirv-val. Os nove shaders novos são obrigatórios e validados no build, incluindo presença de Float16, Fma e NoContraction nos caminhos aplicáveis; falha neles interrompe a compilação em vez de entregar uma bateria vazia.
- Testes locais: oito suítes Java; referência C++ comparada com conversões de precisão do host para o corpus, empates/cancelamento e round-trip de 24.576 representações half; UBSan sem erro. Shaders novos gerados/validados com shaderc 2023.2 e SPIRV-Tools 2023.1; sintaxe C++ com headers Vulkan v1.4.321. Build Android e execução no S24 FE são verificações separadas.
- Referências: https://www.amd.com/content/dam/amd/en/documents/radeon-tech-docs/instruction-set-architectures/rdna3-shader-instruction-set-architecture-feb-2023_0.pdf ; https://github.khronos.org/SPIRV-Registry/extensions/KHR/SPV_KHR_float_controls.html ; https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_shader_fma.html .

## 0.11 — operandos HP e resultados FP32 para RADV/ACO
- Dois novos cartões: **HP operandos / RADV** e **Evidências HP operandos**. A coleta completa inclui os relatórios bruto e resumido: 23 ao todo. As baterias FMA 0.9 e HP 0.10 permanecem disponíveis.
- 27 shaders SPIR-V obrigatórios: nove caminhos em modo padrão, RTE16/RTE32 e RTZ16/RTE32. Com subgroup padrão/32/64, são até 81 configurações por GPU. Cada configuração executa duas fases com 64 lanes. Modos e tamanho de subgroup só são solicitados quando anunciados.
- Caminhos: Fma half com coeficientes por lane; Fma half com coeficientes uniformes via push constants; negação de A; abs(A) e negação de C; mul/add half por lane e uniforme; Fma de half promovido com resultado FP32; controle split com NoContraction; seleção da metade alta de B/C. A alocação SGPR/VGPR e os modificadores efetivos são observados na ISA, nunca deduzidos do GLSL.
- Corpus determinístico finito com B/C assinados e variáveis, entradas FP32 perto de fronteiras half e cancelamento conhecido: 16.015625 × 16.015625 − 256.5 produz 2^-12 com fusão e zero com produto half arredondado em RTE. A fase `matched_sources` usa B=0x4c01 e C=0xdc02 em todas as lanes, permitindo comparar os caminhos uniforme e por lane com os mesmos valores. Na primeira fase as metades baixa e alta de B/C são independentes. Uniform push mantém os coeficientes uniformes nas duas fases.
- Referência inteira em unidades de 2^-48, com 16 modelos de saída **em bits FP32**: conversão inicial seguida de FMA half, split half, FMA FP32 ou produto half + soma FP32; conversão final após FMA/split FP32 ou conta ideal; e FMA/split FP32 sem conversão final. Os modelos assumem RTE32 e ignoram sinais de zero. O corpus exclui resultados half subnormais, NaN e infinitos; não constitui cobertura geral desses valores.
- Resumo por shader: modelos de cada fase, fingerprint SPIR-V, FloatMode, presença efetiva de hp, OP 0x1d/0x1e quando o formato VOP3P é reconhecido e fontes/modificadores no texto da ISA. Contagens se referem a testes, não ao número de unidades físicas. Uma correspondência pode ser ambígua e descreve o shader completo. Nenhuma instrução WMMA é exercitada nesta bateria.

## 0.13 — comparar HP/MIX com arredondamento efetivo rastreado
- A captura v0.12 mostrou `s_round_mode 0xF` antes de HP 0x1d no modo solicitado RTZ16/RTE32, enquanto a referência MIX 0x20 não o inseria. A diferença numérica entre esses shaders não isola uma diferença intrínseca dos opcodes: o estado de arredondamento também mudou. Esta versão registra e classifica esse fator explicitamente.
- **HP posições FP32** passa de três para cinco modos: padrão, RTE16/RTE32, RTZ16/RTE32, **RTZ16/RTZ32** e **RTE16/RTZ32**. Acrescenta 24 shaders SPIR-V obrigatórios e até 72 configurações por GPU, totalizando **180 configurações / 360 fases** nessa bateria. O suporte RTZ32 é consultado e registrado. Combinações mistas exigem independência de arredondamento; modos não anunciados são pulados. A coleta completa permanece com **25 relatórios**.
- O analisador `HpModeLab` parte do `FloatMode` inicial e acompanha `s_round_mode` e `s_denorm_mode` em ordem de instrução. Mostra `HP_MODE_TRACE`, mudanças e `HP_FMA_STATE` com arredondamento FP32/FP16 e o byte FP_MODE (round + denorm) no ponto da FMA. Isso é inferência estática para a ISA MGFX2, baseada no layout RDNA, **não leitura do registrador físico**.
- A reconstrução exige ISA MGFX2, metadados consistentes, instruções contíguas desde o endereço zero e término reconhecido. Falta de dados, gaps, escritas de registrador não acompanhadas e fluxo de controle ficam como UNKNOWN. Prefere a primeira desassemblagem AMD, evitando contar a cópia KHR novamente. Não injeta opcodes nem altera os shaders do driver após compilados.
- Nas comparações mul/add versus Fma promovida, só marca um par como mesmo FP_MODE quando ambos os shaders contêm exatamente uma FMA, os opcodes emitidos são HP 0x1d e MIX 0x20 e os bytes FP_MODE inferidos coincidem naquele ponto. Exibe pares com estado igual/diferente/desconhecido e contagens numéricas exclusivas dos pares de estado igual. As demais contagens continuam observacionais. Igualdade de FP_MODE é um controle adicional; não prova equivalência geral das instruções ou do shader inteiro.
- Reanálise da captura v0.12: reconstruiu os estados dos **81 testes HPO e 108 HPR**. Os pares RTZ16/RTE32 com diferenças de um ULP foram classificados com FP_MODE distinto (0xCF versus 0xCC), e não como comparação com estado igual. Os pares padrão e RTE16/RTE32 correspondentes tiveram estado igual e saídas iguais nessa captura. Isso verifica a análise dos dados antigos; os modos RTZ32 novos dependem da próxima execução no aparelho.
- Validação: 12 suítes Java, quatro testes C++ dos modelos com UBSan; testes específicos do controle de suporte dos cinco modos e seleção do modelo split. Novos testes cobrem sobrescrita dinâmica do estado inicial, pares iguais/diferentes/desconhecidos, ISA parcial, fluxo de controle, alvo desconhecido, inconsistência entre encoding e modo textual, escrita de denormais e metadados conflitantes. Os 24 shaders novos foram compilados e validados por SPIRV-Tools; sintaxe C++ verificada com os headers Vulkan fixados.
- Referência: AMD RDNA3 ISA, seções 3.4.2 e 6.8, campos FP_ROUND/FP_DENORM e S_ROUND_MODE: https://gpuopen.com/download/rdna3-shader-instruction-set-architecture-feb-2023.pdf . A interpretação desse layout na MGFX2 é uma hipótese apoiada pela ISA e pelos resultados observados; não é documentação oficial completa da Samsung.


## 0.14 — casos especiais e desempenho para RADV/ACO
- Dois novos relatórios RAW (27 na coleta completa). **HP especiais / RADV**: 36 shaders, até 108 configurações com wave padrão/32/64; 64 entradas por shader, posições FP32 A/B/C, Fma half, Fma promovida, resultado half empacotado em low/high com sentinela normal na outra metade. Inclui zeros com sinal, subnormais FP32 e limites half, overflow, infinito e NaN quiet/signaling nos bits de entrada; outros operandos têm quatro contextos, inclusive subnormal/Inf. Registra bits brutos e subgroup. Não exige igualdade de payload NaN nem atribui o resultado a uma instrução isolada.
- Modos default, DenormPreserve 16/32 + SignedZeroInfNanPreserve 16/32 e DenormFlushToZero 16/32 + SignedZeroInfNanPreserve 16/32. Os modos explícitos só executam se o driver anunciar todas as propriedades correspondentes. As duas larguras pedem o mesmo comportamento; não há hipótese de independência entre elas. A conversão unpack/pack também pode modificar valores. Uma sentinela preservada demonstra apenas o resultado lógico do shader, não uma escrita parcial física no VGPR.
- **HP desempenho / RADV**: 12 shaders (3 candidatos de precisão × 2 topologias de dependência × 2 tamanhos de dispatch), até 36 configurações. Cada invocação realiza 256 iterações com quatro chamadas Fma e grava quatro saídas. Uma cadeia dependente ou quatro independentes; 1 ou 32 workgroups de 64. FP16, FP32 promovido e packed FP16 são candidatos de compilação, não seleção garantida de HP/MIX. Um warmup + sete amostras, timestamps GPU quando suportados, wall time separado, checksum e comparação de todas as palavras com warmup. Mediana somente com sete amostras GPU positivas. Não é latência isolada de opcode nem pico teórico; conferir ISA, tamanho de wave, VGPR, loop e condições térmicas.
- SPIR-V novo obrigatório, validado no build; Fma, Float16, conversões e presença de loop/quatro chamadas são verificados. Exportação offline: tools/export_hp_extra.py transforma capturas HPE em CSV de regressão com bits brutos, classificação da saída, identificação do shader e opcodes observados; exporta HPB separadamente. Nenhum opcode é forçado, nenhuma configuração do sistema ou do RADV é alterada.
- Validação de host em CI cobre corpus, modos, sentinelas e checksum. Build Android e execução física precisam passar separadamente.


## 0.15 — execução independente via HAL RADV (CLI ARM64)
- Executável separado. O APK continua usando o loader normal; não instala/substitui driver do sistema. O CLI carrega apenas a biblioteca fornecida por dlopen/HMI e resolve funções de instância e dispositivo no HAL. Sem fallback para libvulkan do sistema. Confere VK_DRIVER_ID_MESA_RADV e nome Xclipse 940 antes de executar; registra identidade, firmware, kernel e hashes via runner.
- No WSL/Linux, configure ANDROID_NDK_HOME e MESA_SRC (checkout do fork radv-xclipse com headers Android), glslc e SPIRV-Tools. Execute:
    bash tools/build_radv_direct.sh
    bash tools/run_radv_direct.sh build-radv-direct/radv-direct /path/to/vulkan.radeon.so smoke
  Depois de validar o smoke, rode individualmente roles, special, bench, dynamic. O runner habilita a opção ALU cooperative matrix do fork; isso não significa WMMA nativa. Guarde report.txt, hashes, exit.txt e contadores. Pare ao primeiro timeout, device loss ou reset; não repita automaticamente.
- 12 shaders adicionais (A/B/C, FP16 e FP32 promovido, 1/32 workgroups) com limite de iterações lido de SSBO e limitado a 256. Cada iteração converte fonte FP32 dependente do índice e faz quatro chamadas FMA; até 36 configurações com waves default/32/64. O benchmark contém conversões, atualizações do loop e stores, não mede latência isolada.
